Everything in this workshop runs on any of these four. This page is the lookup table for the places where they differ. Versions and facts were checked against each vendor's documentation on 1 October 2026; the exact pages are listed at the bottom.

<Aside type="caution">
Claude Code was exercised end to end while building this guide. The Codex CLI column was tested with Codex CLI 0.160.0 through OpenRouter: the sandbox home, `AGENTS.md`, skills, hooks, MCP, custom agents, headless flags and the worktree flag. The Cursor CLI column was tested with Cursor CLI 2026.10.01 on a Free plan: the sandbox variable, `AGENTS.md` and `CLAUDE.md`, skills, the OpenSpec commands, hooks, MCP, subagent loading, the worktree flag and headless flags. Not testable on that plan: named models, a full propose and apply run, and `--force` file writes. The Gemini CLI column was tested headless with Gemini CLI 0.62.0 on a free AI Studio key on 2026-10-02: the sandbox home, the API key, `AGENTS.md` through the settings file, skills, the `BeforeTool` hook, MCP, subagents (after acknowledgement), the worktree flag and the headless flags. Signing in with a personal Google account failed. Not tested: the interactive-only steps (`/mcp list`, `/skills list`, menus, the agent acknowledgement prompt, TOML slash commands) and a full orchestrator loop with Gemini or Cursor.
</Aside>

## The sandbox

| | Claude Code | Codex CLI | Gemini CLI | Cursor CLI |
|---|---|---|---|---|
| Fresh home | `CLAUDE_CONFIG_DIR=<dir> claude` | `CODEX_HOME=<dir> codex` (directory must exist; the home is not created for you) | `GEMINI_CLI_HOME=<parent> gemini` (creates `<parent>/.gemini`; run and confirmed on 2026-10-02) | `CURSOR_CONFIG_DIR=<dir> agent` (moves only the CLI config, the sign-in record and chats; MCP servers, hooks, skills and transcripts still come from `~/.cursor` and `~/.claude`; disable servers with `agent mcp disable <name>`) |
| Sign in again | `claude auth login` | `codex login`, or with OpenRouter set `OPENROUTER_API_KEY` and `model_provider = "openrouter"` in `$CODEX_HOME/config.toml` (`codex login status` still says not logged in) | `GEMINI_API_KEY=<key>` from Google AI Studio, then choose "Use Gemini API key". Tested headless with 0.62.0; a free key allows about 20 requests a day per model, so plan on a paid key. A stale `security.auth.selectedType = "oauth-personal"` breaks headless runs: remove it. Headless in a new folder needs `GEMINI_CLI_TRUST_WORKSPACE=true`. "Login with Google" with a personal account failed on 2026-10-02: "This client is no longer supported for Gemini Code Assist for individuals" | `agent login`. `--model <id>` is saved as the default. Named models need a paid plan; Free allows only `auto` |
| Still loads | project `AGENTS.md`, `.claude/`, `.mcp.json` | project files, `~/.agents/skills` (rename it to hide it), and Codex's bundled skills, always | project `.gemini/` | project `.cursor/`, plus your global `~/.cursor` MCP servers, hooks and skills, and `~/.claude/skills` |

## One instruction file: AGENTS.md

| Harness | Reads `AGENTS.md`? | Condition |
|---|---|---|
| Codex CLI | Yes, it is the native file | Always, from the repository root down |
| Cursor | Yes | Root and nested folders; the CLI also reads a root `CLAUDE.md` |
| Claude Code | Yes, from 2.1.277 | Only when there is no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in the folder or any folder above it |
| Gemini CLI | Not by default | Commit `.gemini/settings.json` containing `{"context": {"fileName": ["AGENTS.md", "GEMINI.md"]}}` |

So the demo repository has one `AGENTS.md`, no `CLAUDE.md`, and a two-line `.gemini/settings.json`. That is the whole cross-harness story for instructions.

## Skills

| Harness | Project skills folder | Invoke |
|---|---|---|
| Codex CLI | `.agents/skills/<name>/SKILL.md` | `$name` in a prompt, or picked by description |
| Cursor | `.agents/skills/`, `.cursor/skills/`, and for compatibility `.claude/skills/` | `/name` |
| Gemini CLI | `.agents/skills/` or `.gemini/skills/` | Activated by the model (`activate_skill`); ask for it by name. Not `/name`: Gemini slash commands come only from `.gemini/commands/**/*.toml` |
| Claude Code | `.claude/skills/<name>/SKILL.md` | `/name`, or picked by description |

`.agents/skills/` is read by three of the four. The demo keeps skills there and gives Claude Code a symbolic link, `.claude/skills -> ../.agents/skills`. The `SKILL.md` format is the same everywhere: YAML frontmatter with `name` and `description`, then the instructions.

## Subagents and worktrees

| | Claude Code | Codex CLI | Gemini CLI | Cursor CLI |
|---|---|---|---|---|
| Subagent definitions | `.claude/agents/*.md` | `.codex/agents/*.toml` | `.gemini/agents/*.md` (each project agent must be acknowledged on first use) | `.cursor/agents/*.md` (also reads `.claude/agents/`) |
| Pick a model per agent | `model:` in frontmatter | `model` in the TOML | `model` in frontmatter | `model` in frontmatter |
| Run in parallel | Yes, up to 20 at once | Yes, on request | Not documented | Yes, several Task calls in one message |
| Native worktree | `claude -w <name>`, or `isolation: worktree` on a subagent | `codex --worktree`: a managed detached worktree under `$CODEX_HOME/worktrees`, no name or base; for a named branch use `git worktree add --no-track origin/main` and `codex -C <dir>` | `experimental.worktrees: true`, then `gemini -w <name>`: creates `<repo>/.gemini/worktrees/<name>` inside the repo on branch `worktree-<name>` from the current HEAD (git-ignore it, or use `git worktree add` and start `gemini` in that folder) | `agent -w <name> --worktree-base main`: creates `~/.cursor/worktrees/<repo>/<name>` even with `CURSOR_CONFIG_DIR` set; the default base is the current HEAD; setup scripts come from `.cursor/worktrees.json` |

## Hooks

| | Claude Code | Codex CLI | Gemini CLI | Cursor CLI |
|---|---|---|---|---|
| File | `.claude/settings.json` under `hooks` | `.codex/hooks.json`; each hook also needs trust (`/hooks` in the TUI) or it does not run | `.gemini/settings.json` under `hooks` | `.cursor/hooks.json` with `"version": 1` (the command arrives as top-level `command`; exit 2 blocks, exit 1 does not). The CLI also runs `.claude/settings.json` hooks |
| Before a tool runs | `PreToolUse` | `PreToolUse` | `BeforeTool` | `preToolUse`, `beforeShellExecution` |
| When the agent stops | `Stop` | `Stop` | `AfterAgent` | `stop` |
| Timeout unit | seconds | seconds | milliseconds | not documented |

The workshop's gates are git hooks, not harness hooks, precisely so they work the same in all four. Harness hooks appear once, in act 3, to stop an agent bypassing the git hooks.

## Headless, for the orchestrator loop

| Harness | Command | Model flag | Let it edit files |
|---|---|---|---|
| Claude Code | `claude -p "<prompt>" --output-format json` | `--model sonnet` | `--permission-mode acceptEdits` |
| Codex CLI | `codex exec "<prompt>" --json` | `-m <model>` | `--sandbox workspace-write` |
| Gemini CLI | `gemini --approval-mode yolo -o json -m <model> -p "<prompt>"` | `-m <model>` | `--approval-mode yolo` (`auto_edit` removes the shell tool headless; `yolo` runs every command with your user permissions). `-m` is required in the loop: without it Gemini CLI picks `gemini-3.1-pro`, which a free key cannot use at all. On 2026-10-02 a real run with Gemini CLI 0.62.0 and a free AI Studio key failed: with no `-m` flag, Gemini CLI chose `gemini-3.1-pro`, which has no free quota, and the harness exited 173 before doing any work (429 "Quota exceeded ... free_tier_requests, limit: 0, model: gemini-3.1-pro"). The loop's guards worked: it logged the failure, stopped at the iteration cap (MAX_ITERATIONS=1), and left the ticket untouched. The loop has not completed a run with Gemini. |
| Cursor CLI | `agent -p "<prompt>" --output-format json` | `--model <model>` | `--force` |

<Aside type="tip">
`-p` means prompt in three of the four and profile in Codex. Codex takes the prompt as a plain argument. Cursor's `agent -p` does not wait on stdin (tested). In headless runs, Cursor MCP tool calls need `--force`.
</Aside>
