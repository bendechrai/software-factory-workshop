### Spec-driven artifacts
Source: the built-in `schemas/spec-driven/schema.yaml` and its templates, plus https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md

- `proposal.md`: sections `## Why`, `## What Changes`, `## Capabilities` (with `### New Capabilities` and `### Modified Capabilities`), `## Impact`
- `specs/<capability-path>/spec.md`: the delta. A new capability starts with `## Purpose` of 50+ characters, otherwise `--strict` complains.
- `design.md`: Context, Goals / Non-Goals, Decisions, Risks / Trade-offs, Migration Plan, Open Questions. It is optional ("create only if any apply").
- `tasks.md`: `## 1. Group` headings with `- [ ] 1.1 Task` checkboxes. Apply tracks these checkboxes.

### Delta format
From the schema instructions and https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md:
- Section headers: `## ADDED Requirements`, `## MODIFIED Requirements` (must include the full updated requirement block), `## REMOVED Requirements` (must include `**Reason**` and `**Migration**`), `## RENAMED Requirements` (`FROM:`/`TO:`).
- Each requirement is `### Requirement: <name>` and should use SHALL/MUST.
- Each scenario is `#### Scenario: <name>`. It must be exactly four `#` characters; three fails silently.
- Every requirement needs at least one scenario.
- Scenario lines are bullets: `- **WHEN** ...`, `- **THEN** ...`, `- **AND** ...`.

This file passed `validate --strict` and archived cleanly:
```markdown
## ADDED Requirements

### Requirement: Greeting endpoint
The system SHALL expose `GET /greet` that returns a greeting for the `name` query parameter.

#### Scenario: Greets a named user
- **WHEN** a client requests `GET /greet?name=Ada`
- **THEN** the response status is 200
- **AND** the body is `Hello, Ada!`
```

### Slash commands
Sources: the generated files, https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md and https://github.com/Fission-AI/OpenSpec/blob/main/docs/commands.md

- `/opsx:explore`: thinking mode. It reads and investigates but never writes code, and asks before writing any artifacts.
- `/opsx:propose <idea or name>`: creates the change and all planning artifacts in one go. It stops after planning and does not implement.
- `/opsx:apply`: works through `tasks.md`, ticking boxes as it goes.
- `/opsx:update`: revises the planning artifacts and keeps them consistent. It never edits code.
- `/opsx:sync`: the agent merges the delta specs into `openspec/specs/` itself (optional).
- `/opsx:archive`: runs `openspec archive` and prompts you to sync first.
- Extra profile commands: `/opsx:new`, `/opsx:continue`, `/opsx:ff`, `/opsx:verify`, `/opsx:bulk-archive`, `/opsx:onboard`.
- Documented order: explore -> propose -> apply -> (sync) -> archive.

### Storage: Dolt, not JSONL + sqlite
- The `bd init --help` text says: "Dolt is the default and only supported storage backend". sqlite, postgres and mysql backends have been removed.
- The default is embedded Dolt in `.beads/embeddeddolt/`, which is gitignored.
- `.beads/issues.jsonl` is an optional export (`bd config set export.auto true`), "not the source of truth or a backup".
- Cross-machine sync uses `bd dolt push` / `bd dolt pull`, stored under `refs/dolt/data` on your git remote, separate from your code branches. A fresh clone runs `bd bootstrap`.
- Committed to git: `.beads/config.yaml`, `.beads/metadata.json`, `.beads/.gitignore` and `.beads/hooks/*`.
- Sources: https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md, https://github.com/gastownhall/beads/blob/main/docs/reference/git-integration.md, https://github.com/gastownhall/beads/blob/main/docs/getting-started/sync-setup.md

**Worktrees and branches:** all worktrees share one beads database ("via git common directory discovery"). Issues are not tied to a git branch. Use plain `git worktree add`, or `bd worktree create|list|remove|info`. `BEADS_DIR` overrides where the database lives. Sources: https://github.com/gastownhall/beads/blob/main/docs/reference/worktrees.md and real `bd worktree --help`.

**Hooks:**
- init sets `core.hooksPath` to `.beads/hooks/`, which contains pre-commit, post-merge, pre-push, post-checkout and prepare-commit-msg. These are thin shims that call `bd hooks run <name>`.
- prepare-commit-msg adds an `Executed-By:` trailer.
- `bd hooks install|list|uninstall` manages them. Real `bd hooks list` shows all five as `installed (shim 1.3.1)`.
- **This takes over any existing hooksPath (for example husky).** Use `bd hooks install --chain` to keep existing hooks.

### "Landing the plane" (session completion)
This is the block `bd init` writes into AGENTS.md and CLAUDE.md.

The five steps:
1. File issues for remaining work.
2. Run quality gates.
3. Update issue status.
4. Handle git/sync according to the active profile.
5. Hand off.

The profiles:
- **Conservative (the default):** do not commit, push or run Dolt sync unless asked. Report `git status` and the proposed commands.
- **Team-maintainer (opt-in only):** `git pull --rebase`, `git push`, `git status`.

The older repo AGENTS.md (https://github.com/gastownhall/beads/blob/main/AGENTS.md) says "Work is NOT complete until `git push` succeeds". That is the repo's own policy, which is stricter than the generated default.

[ ] 2. run quality gates        (tests, linters, builds when relevant)
[ ] 3. git status               (check what changed)
[ ] 4. report handoff           (local-only/no remote sync; wait for authority)
```
It also says: never use `bd edit` (it opens an interactive editor), and don't use TodoWrite or markdown TODOs.

### GitHub Pages
Source: https://docs.astro.build/en/guides/deploy/github/

Add `site: 'https://<user>.github.io'` and `base: '/<repo>'` to `defineConfig`. I verified this by building with `site: 'https://example-user.github.io', base: '/example-repo'`:

- The sitemap was generated.
- **Raw `href`s you write in MDX (for example a LinkCard `href`) are NOT auto-prefixed.** Include the base yourself.

Workflow file `.github/workflows/deploy.yml`:
```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout your repository using git
        uses: actions/checkout@v7
      - name: Install, build, and upload your site
        uses: withastro/action@v6

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v5

## D. Security scanners

### gitleaks 8.30.1
Installed locally at /opt/homebrew/bin. Docs: https://github.com/gitleaks/gitleaks

- Install: `brew install gitleaks`, or Docker `zricethezav/gitleaks:latest`, or Linux release binaries.
- **Current syntax: `gitleaks git --pre-commit --staged`.** Real `gitleaks git --help` lists `--pre-commit  scan using git diff` and `--staged  scan staged commits (good for pre-commit)`.
- **`gitleaks protect --staged` still runs in 8.30.1 but is deprecated** (README: "`detect` and `protect` commands are deprecated as of v8.19.0"). It is hidden from top-level `--help`, which lists only completion, dir, git, help, stdin and version.

Real test with a staged fake GitHub token:
```
$ gitleaks git --pre-commit --staged --no-banner --redact
INF 0 commits scanned.
INF scanned ~54 bytes (54 bytes) in 26.4ms
WRN leaks found: 1
EXIT=1
```
- `protect --staged` and `gitleaks dir .` produced the same result (exit 1).
- Exit codes: 0 means clean, 1 means leaks, 126 means unknown flag.
- **Use a realistic test secret in demos.** AWS's documented `AKIAIOSFODNN7EXAMPLE` key was not flagged (exit 0), presumably allowlisted.
- To ignore a finding: a `#gitleaks:allow` comment, or `.gitleaksignore` with fingerprints.
- Recommended hook line: `gitleaks git --pre-commit --staged --redact --verbose`

### osv-scanner 2.6.0
Not installed; commands from the docs. Sources: https://google.github.io/osv-scanner/installation/, https://github.com/google/osv-scanner/blob/main/docs/scan-source.md, https://github.com/google/osv-scanner/blob/main/docs/output.md

- Exit codes: 0 means no vulns, 1 means vulns found, 127 means error, 128 means no packages found.

### semgrep 1.179.0 (Homebrew 1.176.0)
Not installed. Sources: https://docs.semgrep.dev/getting-started/cli-oss, https://docs.semgrep.dev/running-rules, https://docs.semgrep.dev/cli-reference

- Install on macOS: `brew install semgrep`, `pipx install semgrep` or `uv tool install semgrep`. On Linux: pipx or uv. Docker: `semgrep/semgrep`.
- Command: `semgrep scan --config auto`. The docs write it as `semgrep scan --config=auto`. Bare `semgrep --config auto` is the legacy form; I'd use `scan` explicitly.
- No login is needed. However, `--config auto` sends your project URL to the Semgrep registry, and metrics are sent when `--metrics=auto` (the default) and config comes from the registry.
- `--metrics=off` is incompatible with `--config auto` (from memory; **UNVERIFIED**). If metrics must be off, use `--config p/default --metrics=off`.
- Add `--error` so the command exits 1 when there are findings. Without it, findings don't fail the gate.
- Suggested gate: `semgrep scan --config auto --error`
- **UNVERIFIED by execution.**

### Minimal before/after script
Saved as `pw-test/screenshot.mjs`. It follows the pattern at https://playwright.dev/docs/library and uses `npm i -D playwright`.
```js
// Usage: node screenshot.mjs <url> <out.png>
import { chromium } from 'playwright';
import { mkdir } from 'node:fs/promises';
import { dirname } from 'node:path';

const [url, out = 'screenshot.png'] = process.argv.slice(2);
if (!url) { console.error('usage: node screenshot.mjs <url> <out.png>'); process.exit(2); }
await mkdir(dirname(out), { recursive: true });
const browser = await chromium.launch();
const page = await browser.newPage({ viewport: { width: 1280, height: 800 } });
await page.goto(url, { waitUntil: 'networkidle' });
await page.screenshot({ path: out, fullPage: true });
await browser.close();
console.log(`saved ${out}`);
```

**How the test went:**
- Plain `chromium.launch()` failed while the headless-shell download was still in progress: "Executable doesn't exist at .../chromium_headless_shell-1243/...". So headless mode needs the headless shell, which `install chromium` downloads after the full browser.
- With `chromium.launch({ channel: 'chromium' })`, which uses the full Chromium build, it ran against the built Starlight site and printed `saved evidence/before.png`, a 1280x1398 PNG. That copy of the script is saved as `pw-test/screenshot-full.mjs`.
- The plain-launch version should work once the headless-shell download finishes, but **I didn't test it after that point.**
